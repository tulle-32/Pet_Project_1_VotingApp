# Архитектура проекта — подробный разбор

## Общая схема потока данных

```
[Браузер]
    │
    ▼ (через hosts-файл: vote.local / result.local)
[Ingress] — единая точка входа снаружи
    │
    ├──► [Vote]    (Flask, принимает голос от пользователя)
    │        │
    │        ▼ (пишет голос в очередь)
    │     [Redis]   (временное хранилище очереди голосов)
    │        │
    │        ▼ (забирает голос из очереди)
    │     [Worker]  (.NET, обрабатывает голос, пишет в БД)
    │        │
    │        ▼ (записывает результат)
    │     [Postgres] (хранит все голоса постоянно)
    │        │
    │        ▲ (читает текущие результаты)
    └──► [Result]  (Node.js, показывает статистику в реалтайме)
```

Vote и Result не общаются друг с другом напрямую. Они связаны только через общее хранилище (Redis → Worker → Postgres → Result). Компоненты не должны знать друг про друга напрямую — только про то хранилище/очередь, с которым работают.

## Роль каждого компонента

**Vote** — простой веб-сервер (Flask), принимает голос от пользователя. Ничего не хранит сам — сразу кладёт голос в очередь Redis и забывает про него (это называется stateless — компонент без собственного состояния).

**Redis** — буфер между Vote и Worker. Нужен, чтобы Vote не "зависал", ожидая записи в базу — Vote быстро сбрасывает голос в очередь и сразу отвечает пользователю, а реальная запись в БД происходит чуть позже, асинхронно. Если БД временно тормозит, очередь просто накопит голоса, а не завалит систему ошибками.

**Worker** — единственный, кто пишет в базу. Сидит в фоне, постоянно спрашивает Redis "есть новые голоса?", забирает по одному и вставляет строкой в Postgres. У Worker нет веб-интерфейса, к нему никто не подключается по сети.

**Postgres** — единственный источник правды. Здесь хранятся все голоса постоянно, на диске (через PersistentVolumeClaim), переживая перезапуски Pod'ов. Единственный компонент, для которого критично не терять данные при перезапуске.

**Result** — читает из Postgres напрямую (не через Worker, не через Redis), показывает текущую статистику. Как и Vote, сам ничего не хранит — stateless.

**Ingress** — общая входная дверь. Снаружи кластера напрямую к Pod'ам или внутренним Service достучаться нельзя (они видны только внутри кластера, тип ClusterIP). Ingress — единственная точка, которая реально слушает внешний трафик и распределяет его по правилам (vote.local → Vote, result.local → Result).

## Как манифесты технически связаны

### Три уровня labels

Каждый Deployment/StatefulSet использует одну и ту же схему:

```
metadata.labels.app: <имя>               — бирка на самом объекте, для человека
spec.selector.matchLabels.app: <имя>     — по каким Pod'ам этот объект управляет
spec.template.metadata.labels.app: <имя> — какую бирку получат созданные Pod'ы
```

Второе и третье поле обязаны совпадать — иначе Deployment создаст Pod'ы, которые сам не сможет найти, и будет считать, что у него 0 живых реплик.

### Service — как находит свои Pod'ы

Service ищет Pod'ы только по labels, а не по имени Deployment/StatefulSet. Если в selector указано app: vote, он найдёт любой Pod с такой биркой, независимо от того, кто его создал.

- port — порт самого Service (виртуальный, внутри кластера)
- targetPort — порт внутри контейнера (то же значение, что containerPort у Deployment)

У нас эти два числа всегда совпадают, но технически это два разных числа.

### ClusterIP vs Headless Service

| | ClusterIP (по умолчанию) | Headless (clusterIP: None) |
|---|---|---|
| Используется для | Vote, Redis, Result | Postgres |
| Даёт единую виртуальную IP | Да, с балансировкой | Нет |
| DNS отдаёт | Один общий адрес | Адрес каждого конкретного Pod'а |
| Зачем | Не важно, какая реплика ответит | Нужно обращаться именно к конкретному Pod'у |

### StatefulSet vs Deployment

Deployment создаёт взаимозаменяемые, безымянные Pod'ы. StatefulSet (только для Postgres) даёт каждому Pod'у стабильное имя (postgres-0) и свой персональный диск через volumeClaimTemplates — при перезапуске Pod возвращается к тому же диску с теми же данными.

### ConfigMap vs Secret

Оба хранят пары ключ-значение, разница только в предполагаемой чувствительности данных: ConfigMap — для несекретных настроек, Secret — для чувствительных. Secret хранит значения в base64 — это кодирование, не шифрование. Реальная защита — ограничение прав доступа (RBAC), а не сам факт base64.

В этом проекте сознательно решено не добавлять Secret-файлы в .gitignore — пароль учебный, проект наружу не публикуется. Осознанный выбор ради простоты pet-проекта, не рекомендация для продакшн-систем (там — Vault/Sealed Secrets/SOPS обязательны).

### Связи внутри Postgres-компонента

```
ConfigMap.metadata.name  ──► StatefulSet.envFrom[].configMapRef.name   (совпадение по строке)
Secret.metadata.name     ──► StatefulSet.envFrom[].secretRef.name      (совпадение по строке)
Service.metadata.name    ◄─► StatefulSet.spec.serviceName              (совпадение по строке)
```

## Почему у компонентов разное число реплик

Правило: если компонент не хранит данные сам (stateless) — реплик может быть несколько. Если хранит (stateful) или конкурирует за общий ресурс — реплика одна.

| Компонент | Реплики | Почему |
|---|---|---|
| Vote | 2 | Stateless, каждый запрос независим |
| Redis | 1 | Без кластеризации несколько Redis — несинхронизированные копии данных |
| Worker | 1 | Несколько Worker'ов конкурируют за одни и те же сообщения — риск дублирования |
| Postgres | 1 | Хранит данные постоянно; без репликации несколько экземпляров — разные источники правды |
| Result | 2 | Stateless, только читает — конкуренции нет |

## Что нужно перед реальным деплоем

- minikube addons enable ingress — включить контроллер, реально обрабатывающий правила Ingress
- Добавить `vote.local`/`result.local` в `/etc/hosts` — проверено внутри Ubuntu VM; доступ с Windows-хоста отдельно не проверялся
- Применить манифесты рекурсивно: kubectl apply -f manifests/ -R

## Namespace

Все объекты проекта живут в отдельном namespace `voting-app` — логическая перегородка внутри одного кластера minikube, отделяющая ресурсы проекта от служебных компонентов кластера (kube-system: coredns, ingress-controller и т.д.).

Проверка одной командой:
kubectl get pods,svc,deployment,statefulset -n voting-app
